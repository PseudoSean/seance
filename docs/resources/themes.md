# Themes

A theme is one plain CSS file in `client/themes/`, copied by webpack to `public/themes/` and loaded after `css/style.css` through the `<link id="theme">` in `index.html`. Picking a theme in Settings → Appearance rewrites that link's `href` to `themes/<name>.css` (`client/js/settings.ts`); `js/loading-error-handlers.js` does the same from localStorage before the app boots so there is no flash of the wrong theme. There is no preprocessing: a theme's rules simply cascade over the base stylesheet, and the user's custom stylesheet (Settings → Appearance) cascades over the theme. One theme, `ps`, is also the one exception to "one CSS file": it brings a script chunk of its own through a small theme-neutral hook (below).

`style.css` declares its palette as custom properties on `:root` (`--body-color`, `--window-bg-color`, `--link-color`, `--highlight-bg-color`, the `--tok-*` code colours, …) and reads them everywhere it can, so most of a theme is a `:root` block. Where the base stylesheet still has literal colours (the sidebar rows and badges, header icons, the input and the context menu, message-type icons, the mIRC colour table) a theme restates those selectors.

The list the Settings dropdown shows is static, in `client/js/configuration.ts` (`themes`, with a `displayName` and an optional `themeColor` for the browser chrome), and `defaultTheme` there is what a fresh browser gets; a deploy overrides that with `theme` in `config.json` (`docs/resources/branding.md`). A stored theme name the build no longer has falls back to the default at boot (`boot.ts`), which is how browsers that had `default` stored came over to `coffee`.

**To add a theme:** drop `client/themes/<name>.css` in, add its entry to `themes` in `configuration.ts`, and add the name to the list in `test/tests/build.ts`. Start from `creama.css` or `cobalt.css` for another colour direction on the same rules (tokens only), from `morning.css` for a theme on TheLounge's variables.

## The handoff themes

`coffee` and `creama` implement the warm direction of the colour redesign handed off in `docs/resources/themes/` (`README.md`, `ink-amber-theme.md` and the `ink-amber-*.png` mockups); `cobalt` and `frost` implement the cool one, `cobalt-frost-theme.md` with its own mockups. The handoff is colour only, and so are the themes: layout, spacing and type are untouched, and its suggestions beyond colour (a `data-theme` switch, sweeping the components for literal colours, hover/focus/mention states) were deliberately left for later — except the composer's focus ring, which is in: the bar is flush with the window, so `#form:focus-within` draws it as the top edge (accent border plus a 2px inset of `--focus-ring`) and the caret takes the accent (`caret-color`), in `coffee.css` and, through the import, the three token-only themes; `style.css` gives `day` and `morning` the same in their green.

The two directions share every rule. `coffee.css` is the one file with selectors in it; `creama.css`, `cobalt.css` and `frost.css` are token values alone, so a fifth direction is one more `:root` block and costs nothing in bundle size beyond its own colours. The handoff intended exactly that — both directions use the same token names, "so they are drop-in interchangeable".

The custom properties use the handoff's token names (`--chat-bg`, `--rail-accent`, …) so a value can be checked against its tables, plus a few the handoff does not have: the tints (`--tint-soft`/`--tint-strong`, translucent overlays that must be light on a dark surface and dark on a light one), the notice-box pairs (`--note-*`, `--warn-*`, `--error-*`, `--ok-*`), `--menu-bg`, and the message semantics (`--event-join`, `--event-quit`, `--nick-default`, `--notice-color`, `--action-color`). TheLounge's own variables are mapped onto the tokens at the end of `:root`, which is what keeps the rest of `style.css` in step.

Deviations from the handoff, all for contrast (`docs/projects/accessibility.md`), are listed in the header comment of each file, and both light variants needed the same ones: muted text, the link colour, the join green and the placeholder tone are darker than specified because the handoff's own light values missed its 4.5:1 rule (`frost` moves the link blue `#1f6feb` → `#2166e0` and the muted grey `#6b7a8c` → `#65727f`); `coffee`'s footer icons use the light rail's muted tone. Nick colours are the biggest addition: the handoff gives three per variant, `style.css` hashes nicks into 32 slots (`.user.color-1`…`-32`), so each theme carries a generated 32-colour palette — hues swept around the wheel at one oklch lightness and the chroma both directions agree on (0.115), every slot ≥ 4.6:1 on a dark chat surface or ≥ 5:1 on a light one, so a nick still reads on a highlighted row.

The rail gradient is on `body` as well as `#sidebar`, so the gutter `day.css` keeps around the window continues the sidebar instead of stopping at its edge; the two gradients coincide because both span the viewport.

## The `ps` theme

`ps.css` is a fork of the `<3` theme (`heart.css`, whose design record is `docs/projects/heart-theme.md`; the fork's own is `docs/projects/ps-theme.md`, whose plan 1 "the seam" landed 2026-09-24): coffee's rules with its own tokens, and — unlike every other theme — a scene of its own. **Fonts**: Nunito (400–800, an italic 400–700) and Baloo 2 (400–800) ship beside it under `themes/ps/` as Google Fonts' variable woff2 files (fetched once by `tools/heart/fetch-fonts.mjs`, OFL texts alongside), the Latin subset, so other scripts fall back to the system stack mid-line; plan 2 replaces them with Mulish and Fraunces (`docs/projects/ps-theme.md` §8). **Motion**: every `.msg` fades in on insertion, pending copies included — the entrance animations use `backwards` fill (never `both`), so a pending copy settles at the existing pending style's dimmed opacity once its fade ends — the sidebar rows, header and composer rise on load, and a mention glows. The `<3` theme's glitter is gone; `ps.css` does not restate the reaction enter classes, so a reaction pops in with `style.css`'s `reaction-pop` like in every other theme.

**The scene** (`client/js/themeScene.ts`, `client/js/scenes/ps/{engine,colour,palette,scene}.ts`) replaces the old per-conversation meadow: one live sky behind the whole app, the same for every channel, following the viewer's own local clock. `themeScene.ts` is the app's one hook for a theme to bring page elements of its own — a table (`SCENES`) of the themes that have a scene, keyed by name; only `ps` is in it. `settings.ts` calls it when a theme is applied, `boot.ts` wires it to `visibilitychange` (`installThemeSceneHooks`), and `App.vue` tells it what kind of conversation is open (channel, query or neither), for a later plan's frosted private view to key on. Applying `ps` mounts its scene into `#theme-scene`, an empty `<div>` in `client/index.html`; `style.css` keeps it `display: none` for every theme, and only `ps.css` shows it, so the element stays invisible even in the instant between a theme switch and its scene's removal. Switching away destroys the mounted scene. The engine and palette (`engine.ts`, `colour.ts`, `palette.ts`) are Vue-free and DOM-free, so mocha loads them directly (`test/scenes/ps/engine.ts`, `palette.ts`): a `Date` in, sunrise/sunset/season/weather and the sun's and moon's positions out of the engine, then the day's colour table out of the palette. `scene.ts` uses the DOM (never Vue or the store) to build the sky, stars, sun and moon once, then — once a minute, and again the moment the page becomes visible — writes what the engine and palette computed as custom properties on its own root, and publishes on `<html>` the four values the rest of the chrome reads: `data-ps-light` (`day`/`night`), `data-ps-text` (`ink`/`light`), `--ps-halo` (the daytime text glow) and `--canvas-bg-color` (the sky-top colour of the hour, also read by the iOS status bar tint). A hidden page's scene stops outright — CSS and SVG animation paused, no timer — and a scene mounted straight into a hidden page starts stopped rather than running unseen. **Without the chunk** (still loading, failed, or an older build), `ps.css` alone paints a fixed, legible daylight sky and ink text — never an unstyled or midnight page.

**The words over the plains.** With the meadow gone, message text sits straight on the open sky, so `ps.css` carries a block generated by `tools/ps/message-palette.ts` between `/* ps:message-palette:start */`/`:end */` markers: every semantic colour the message column reads (muted text, links, join/quit, notices, the default nick) and both 32-slot nick sweeps, each solved in OKLCH from its token's own hue and chroma to the lightness that clears 4.5:1 with a 0.1 margin against the single worst ground its treatment can meet — computed by `tools/ps/legibility.ts` over nine sampled days, every five minutes, across all six weathers. Two treatments switch on `data-ps-text`: **ink** by day (`#1b2638` on a close pale halo) and **light** the rest of the time (white on a close dark shadow); the floors test (`test/scenes/ps/legibility.ts`) holds every generated colour to that margin, and the spec's own fixed colours (ink, faint ink, white, white at 80%) to the plain 4.5:1/3:1 floors besides. Regenerate after changing a colour table in `palette.ts` or `engine.ts` (which move the worst grounds), or the 32 top-level `.user.color-N` rules or the `--tok-*` bases in `ps.css`'s `:root` (which the generator reads back): `npx tsx tools/ps/message-palette.ts` prints the block and the two worst grounds without touching the file, `--write` replaces the block in place (idempotent — a second `--write` changes nothing). The semantic bases and the spec's own fixed colours are hardcoded in the generator itself, not read from `ps.css`, so retinting `--chat-accent` in the file alone never reaches the column — edit `tools/ps/message-palette.ts` and regenerate.

**The animals**, carried over from the meadow: one layer (`#theme-scene .ps-animals`) with a fixed cast — a horse and a bunny near, a deer far off — sized from `--strip`, the same self-animating SVGs `tools/heart/generate.mjs` produces from the rigs in `tools/heart/rigs/` (README there). **In `ps` they are switched off, not removed**: one block in `ps.css` right after the layer's rule empties its three slots, so nothing is painted and — since no `url()` is left to fetch — nothing is downloaded; deleting that block brings them back.

`test/themes/ps.ts` checks the tokens, the nick palettes' contrast, the fonts, that no glitter is left, and the animal off switch; `test/tests/themeScene.ts` checks the hook in isolation; `test/scenes/ps/{engine,palette,scene,legibility}.ts` check the engine, the palette, the scene's pure exports and the message-column floors. `tools/scenarios/theme-ps.mjs` checks the rest in a browser: the scene mounts only under `ps` and only there, the published values at noon, dusk and night, a hidden page stopping it, a theme switch mounting and unmounting cleanly, the daylight fallback when the chunk is blocked, and that no animal file is ever fetched. Plan 2 (`docs/projects/ps-theme.md` §13) brings the glass chrome and both its palettes, Mulish and Fraunces, and the rendered-pixel α calibration plan 1's message palette still runs without (§11); plan 3 draws the land, the yurt and the weather; plan 4 the embers and the frosted private view.

## The Princess pair

`princess` and `princess_` are a light/dark pair of IRCCloud-style themes, so that switching from IRCCloud costs the users who came from it nothing. Their palettes derive from the IRCCloud client, whose source is published under the Apache License 2.0, and are used here with that attribution; the values are tuned from there against the contrast bar the theme scenario pins. The naming follows IRC's own convention, the underscore being the alt the way a second connection takes one. Both draw nicks in messages bold, as IRCCloud does, and leave the member list at the regular weight it has there.

`princess` is the first theme here with a **light rail** — its buffer drawer is pale blue (`#d9e7ff`), not a dark gutter, so `--rail-*` inverts relative to every other theme. That inversion is what exposed a long-standing bug in `tools/scenarios/themes.mjs`: the check paired the selected channel's label against `--body-bg-color`, the rail surface, when the selected row has a background of its own. On four dark-rail themes a near-white label cleared 4.5:1 against the rail by accident, so the check had been passing for the wrong reason.

Both are also the first to use **row bands** — whole rows tinted by kind, so `.msg.self`, notices and server events each take their own background. Those restate selectors rather than tokens, and they work without touching `style.css` because the hover band is painted as a `background-image` gradient (see the message hover state above), leaving `background-color` free for the row. A mention row still wins over both from `style.css`'s more specific selector.

**In `princess`, the mention row is the constraint that shapes the rest.** `#c0dbff` is a strong tint, so everything drawn over it must clear 4.5:1 against it rather than against white. That is why its 32 nick slots are darker and less saturated than a white-only palette would need — 20 hues carried over, 12 more filling the widest gaps, each at the lightest tone that still passes on white, on the own-message tint and on the mention row (worst slot 4.60:1) — and why links are restated at `#1558c9` on the notice and mention bands. Four other values are darkened along their own hue, each checked on the surface it sits on: timestamps `#aaa` → `#5f5f5f`, the collapsed-row and placeholder grey `#afafaf` → `#898989`, links `#1e72ff` → `#1b69ed`, the inactive buffer `#9cc7ff` → `#516989`; the selected-buffer blue drops to `#1d6ef8` so its white label clears the bar.

`princess_` inverts the problem. Its chat surface is `#000000` and its bands climb in near-black steps — `#191919` server events, `#1f2530` own messages (the one cool band, so it tells apart from the events band five points below it), `#262626` notices, `#2b2b2b` a mention — so the band a row sits on barely changes what its text has to clear. Two values are lifted: timestamps `#8c8c8c` → `#929292`, the unread blue `#1e72ff` → `#2993ff`. One departure is deliberate: the palette it started from is greyscale, with a grey accent, but Seance draws links in the accent and a grey link is indistinguishable from body text — so the accent is the lifted blue and the grey becomes `--tok-punctuation`.

Both carry the classic mIRC 16 rather than `style.css`'s flat palette; slots 0, 1 and 16–98 already match, so only 2–15 are restated. In `princess` codes 8–11 stay low-contrast on white, and in `princess_` codes 2, 5 and 12 are left to `coffee.css` entirely — navy, maroon and pure blue cannot reach 4.5:1 on black, blue saturating at 2.44:1. A colour code is the sender's choice rather than the theme's.

## Your own messages

`style.css` greys an own message's text to `--body-color-muted`, TheLounge's look, and a theme was free to band the row instead (the Princess pair). The grey is hard to read on an iPhone under a dark theme — a system setting there flattens it into the background, which Android and a desk do not do — so the choice is the user's, not the theme's: Settings → Appearance → Your own messages picks **greyed text** (the default, every theme as it was), a **highlighted row** (the text like everyone else's, the row on a band) or **nothing**. The value lands on `<html data-own-messages>` (`client/js/helpers/ownMessages.ts`, `settings.ts`) and the three looks are rules in `style.css`, so no theme file needs to know about it. The three do not overlap: a band a theme paints on `.msg.self` itself (the Princess pair, Keeki) shows under **highlighted row** only, in the colour the theme names with `--own-bg` (without one the band is the text colour at 7% over the row). Own join and mode lines are `.self` as well and are left to the theme in every mode: the band is for what was said. Browser check: `tools/scenarios/own-messages.mjs` (coffee and princess, every setting, a reload).

## Checking a theme

`yarn test` never loads a stylesheet. Build, serve `public/`, and look (`docs/resources/browser-testing.md`); the Appearance dropdown switches live. `tools/scenarios/themes.mjs` drives that dropdown through every theme against the dev ircd, checks the stylesheet link, the stored name and the browser chrome colour, measures the pairs above on the four handoff themes (text, timestamps, links, the join line, a nick on a highlighted row at ≥ 4.5:1; icons and the placeholder at ≥ 3:1) from computed styles, and leaves a screenshot of the chat under each theme.
