# Translating Seance — the `.po` workflow

Every UI label in Seance is rendered through one translation function (`t()`/`tCount()` from `useI18n()`, or the same resolver in the service worker), backed by gettext `.po` catalogs. This document is the fill-in workflow for a human translator or a machine-translation (MT) pipeline: where the table is, how to fill a row, how to keep a translation alive across upstream merges, and the two structural rules (`{var}` placeholders survive verbatim; a key is a whole translatable phrase) that a pipeline must not "helpfully" violate. The implementation status and label counts live in `docs/projects/i18n.md`.

## The table

`client/locales/messages.pot` **is** the output table: a flat gettext template — one entry per label, no `LC_MESSAGES` nesting. The columns map to the `.po` keywords like this:

| Table column     | gettext part  | Example                                                          |
| ---------------- | ------------- | ---------------------------------------------------------------- |
| Label key        | `msgctxt`     | `"connect.submit"` — a stable semantic identifier                |
| Context          | `#.` comments | _"Button on the connect form: submits it and dials the server."_ |
| Source text (en) | `msgid`       | `Connect` — plain English                                        |
| Translation      | `msgstr`      | empty in the template — the column to fill                       |

A filled row reads:

```po
#: client/components/Windows/Connect.vue
#. Button on the connect form: submits it and dials the server.
msgctxt "connect.submit"
msgid "Connect"
msgstr "Verbinden"
```

The `#.` context is written for humans _and_ machines: it says what the label is and does (a button? a tooltip? an aria-label heard by a screen reader?), where it appears, and what any `{var}` carries. Read it before translating — the `msgid` alone is often too short to disambiguate ("Close" the window vs "Close" the channel). `#:` lines above the context record where the label is rendered; they are maintained by the tooling and can be ignored while translating.

The file header (the first entry, `msgid ""`) carries `Language:` and `Plural-Forms:` — the template ships `Plural-Forms` preset to English's default (`nplurals=2; plural=(n != 1);`) and only `Language:` is empty; a real `.po` must have both filled in (below).

## Filling in a language

1. Copy the template to the per-locale table: `cp client/locales/messages.pot client/locales/<tag>.po` (e.g. `de.po`). The file name **is** the locale tag the rest of the pipeline keys on — BCP-47, lowercase base where possible (`de`, `pt-BR`).
2. Fill the header: `Language: de` and a `Plural-Forms` line taken from `tools/i18n/plural-rules.json` (see § Plurals — the file must carry one line for the tag before compiling).
3. Fill the `msgstr`s — by hand in any `.po`-aware editor, or by feeding the `.po`/`.pot` to an MT pipeline. The `msgid`s are plain English sentences, which is exactly what MT tools expect; the `#.` context can be passed along as prompt/instruction material. The context is metadata: never let a pipeline translate into `msgctxt`, `#.` or `#:` lines.
4. Compile: `yarn i18n:compile` (`npx tsx tools/i18n/compile.ts`). This compiles the pot → `client/locales/en.json` and every `client/locales/<tag>.po` → `<tag>.json`, regenerates the locale list (`client/js/i18n/available.ts` and `tags.json`), and **fails loudly** on problems: a translation that lost a `{placeholder}` its msgid has names the key and stops the run; a `#, fuzzy` entry is skipped with a stderr warning (en serves that key) rather than half-applied.
5. Build and look at it: see § Verifying a translation.

Compile details worth knowing:

- `en.json` is compiled from the pot itself — the msgids _are_ the English copy; there is no separate English source. This is why the pot is the single source of truth and why an English copy change is a `msgid` change (§ Keeping a translation alive).
- A `<tag>.json` overlay contains **only the entries that carry a translation**. The runtime resolves `catalog[tag][key] ?? en[key] ?? key`, so an untranslated or fuzzy-skipped key silently falls back to English — a partial translation is always shippable.
- Untranslated plural slots are simply absent. The runtime's category lookup (`core.ts`) resolves the active category, then `other`, then the first filled category, then the key itself — English serves only when the whole key is untranslated (absent from the overlay). Consequence: a **partially** filled plural renders the first filled slot's text for the missing categories — never English — so an MT pipeline must not rely on en covering a half-filled plural: fill every `msgstr[N]` or none.

## Placeholders, whole phrases, and the two shapes

Two structural rules keep the catalog translatable. An MT pipeline that breaks either produces English-looking output that is broken in every language; the compiler catches the first, nothing can catch the second at build time.

**A key is a complete translatable phrase — never concatenate translated fragments.** Word order differs too much between languages for "label A + label B" composition to work. When a sentence needs a value inside it, the key carries a `{var}` placeholder and the whole sentence is one key:

```po
#. Notification title for a message in a channel: {nick} is the sender's
#. nickname, {target} the channel name. Translated as a whole so word order
#. is free; the unread-count suffix is appended after it, never inside.
msgctxt "sw.titleChannel"
msgid "{nick} in {target}"
msgstr "{nick} in {target}"
```

A German translation is free to reorder the frame around its variables — `"{target}: {nick}"`-shaped word order is exactly what placeholders are for; a fragment pair `"in"` + `"{target}"` glued together in code is not. The worked counter-examples are everywhere user content meets a frame: `connection.error` carries the server's or browser's technical text **verbatim** in `{message}` (`"Connection failed: {message}"`-shaped keys never reword `{message}`), and system-message frames wrap `<bdi>`-wrapped nicks with a frame key such as `msg.join` ("has joined the channel") instead of building "alice" + "has joined" + "the channel" from parts.

Rules for pipelines and translators:

- `{name}` tokens must survive **verbatim** — same set, same spelling; moving them inside the sentence is expected and correct, dropping, renaming or translating inside the braces is a broken row (compile fails with the key named).
- User content passed into `{vars}` (nicks, channel names, server text) is substituted at runtime and must not be inflected around: do not add grammar that assumes the variable's form (article gender, case endings) — prefer frames that keep the variable at a phrase boundary when the target language makes that necessary.
- Never split a sentence into several keys to "reuse" a word; if two labels genuinely share a phrase, they are two keys, each a whole phrase.

**Flat keys vs plural keys — both shapes exist on purpose.** Most keys are flat: one `msgid`, one `msgstr` — labels, verbs, tooltips, whole sentences (`cmd.lobbySend`, `cmd.usageJoin`, `connect.submit`). Keys rendered through `tCount()` are plural entries: they carry `msgid_plural` and one `msgstr[N]` per plural form of the language, and the compiler evaluates the tag's `Plural-Forms` expression for n = 0…199, cross-references `Intl.PluralRules(tag)`, and emits the text keyed by CLDR category (`{"one": …, "other": …}` for English; Russian compiles to `one/few/many/other`, Arabic to all six):

```po
#. Condensed block: {count} users joined while the block was collapsed.
msgctxt "condensed.join"
msgid "{count} user has joined"
msgid_plural "{count} users have joined"
msgstr[0] ""
msgstr[1] ""
```

Fill `msgstr[N]` exactly as gettext expects (`nplurals` slots, in the expression's index order — the `Plural-Forms` header's). Do **not** "fix" a flat key into a plural or a counted key into a flat one: the shape is chosen by the call site (`t()` vs `tCount()`), and a flat verb like `cmd.lobbySend` has no number to agree with. The English source of a plural entry is always the _singular_ first — the msgid — even where English uses the plural for most counts; that is gettext's layout, not a typo.

## What is never translated

The catalog is UI chrome and client-authored copy **only**. Never translated, never passing through `t()`, therefore never present in the `.po` files — and MT pipelines are never pointed at any of it:

- message bodies (own or anyone's), topics, MOTD, away/kick/part reasons, CTCP content, WHOIS output, channel lists, ban lists — anything a user or the ircd typed;
- usernames/nicks and channel names — they render verbatim, wrapped in `<bdi>` where they sit inside a translated frame;
- **server text** — numeric replies, `FAIL`/`WARN` payloads, the IRC server's own words. `connection.error`'s `{message}` is the server's or browser's technical message verbatim inside a translated frame: translate the frame, never the placeholder's content;
- brand names — `Seance` in the worker's fallback notification title included (the worker cannot read a deploy's `appName` today);
- dates, times, numbers, list conjunctions and sorting — `Intl.DateTimeFormat`/`NumberFormat`/`ListFormat`/`Collator` produce these per active locale (`client/js/i18n/dates.ts`); the only catalog copy in that area is `dates.today`/`dates.yesterday`.

A translator meeting English prose in the wild (a server notice, a user's message) is looking at data, not at a missing row.

## Keeping a translation alive

After an upstream merge or any pot change, sync every `.po` against the pot:

```sh
yarn i18n:merge                      # every client/locales/*.po
yarn i18n:merge de                   # one
```

`yarn i18n:merge` runs `tools/i18n/merge.ts` (msgmerge-lite) and keys entries by `msgctxt`: a translation survives an exact `msgid` match; a drifted `msgid` is re-adopted from the pot and the entry is marked `#, fuzzy` for review (the old translation is kept as the draft); keys new to the `.po` are appended with empty `msgstr` slots; keys the pot no longer carries are dropped. The `Language`/`Plural-Forms` headers are rewritten from `plural-rules.json`. It never invents translations.

- **Keys are stable identifiers.** A key rename is not a translation-preserving operation — merge would drop the old key and add the new one empty. When the English copy changes, change the `msgid` (via `tools/i18n/add.ts`, below) and keep the key; `merge.ts` then marks the entry fuzzy and the translation survives as a draft to re-review. Rename keys only when the _meaning_ changes, and let `merge.ts` do the bookkeeping — never by hand inside a `.po` (a hand-renamed `msgctxt` is exactly a drop-plus-add, with the translation lost).
- Fuzzy is reviewed, then un-fuzzied by removing the flag by hand (the one sanctioned hand edit alongside filling `msgstr`s); compile skips fuzzy entries either way.
- There is no `en.po`: the pot compiles straight to `en.json`. Likewise `qqx` (§ Verifying) has no `.po` — it is generated.

## Adding a language

1. Add one line to `tools/i18n/plural-rules.json` — the tag and gettext's C plural expression (`{"nplurals": 4, "expr": "(n%10==1 && n%100!=11 ? 0 : …)"}` for Russian). The expression is restricted to arithmetic; `compile.ts` refuses anything else.
2. Copy the template to `client/locales/<tag>.po` and fill it (§ Filling in a language).
3. That is all: `yarn i18n:compile` picks the file up, regenerates `available.ts`, and the language selector (Connect form and Settings → Appearance) lists it automatically. `en` and `qqx` are compiled from the pot/generated — a hand-written `en.po` or `qqx.po` is refused.

## Verifying a translation

```sh
yarn i18n:compile                                        # compile + validate
npx tsx tools/i18n/check.ts                              # pot ↔ call-site agreement (also run inside yarn test)
NODE_ENV=development npx tsx tools/i18n/compile.ts \
  && NODE_ENV=development npx webpack                    # a servable development build
python3 -m http.server -d public 8000                    # serve, pick the language in the selector
```

- **The compile and the webpack build must run with the same `NODE_ENV`.** `compile.ts` bakes the build flavor into `available.ts` (`DEV = NODE_ENV !== "production"`) and into the tag lists: a dev-mode compile flips `DEV = true` and lists `qqx` in `available.ts`/`tags.json` — that is what makes the pseudo-locale appear in the selector (and what production builds hide). A development webpack build **without** a fresh dev compile presents the committed production-flavored catalogs — the build recipe is the two commands above, in that order. `yarn build` (production) already runs `i18n:compile` first.
- `yarn i18n:check` (`tools/i18n/check.ts`) cross-checks the pot against the live tree: every `t()`/`tCount()` call-site key exists in the pot, every pot key is referenced, every key carries `#.` context. It runs inside `yarn test` (`test/tests/i18n-toolchain.ts`, live-tree assertion), so a stale pot fails the suite.
- **`qqx` is the eyeball rig, not a language**: a generated pseudo-translation of `en` (accented lookalikes, doubled length, RTL-wrapped) listed in the selector only in development builds. It exercises direction, doubling-driven overflow and the plural plumbing with zero translation effort. **It never ships — at any layer**: a production compile omits it from `available.ts`/`tags.json` (so the pre-paint script and `activate()` reject a stored qqx pick — a settings restore from a dev machine falls back to the automatic resolution), the selector does not list it, and webpack does not copy `qqx.json` into `public/locales/`. A real locale is verified the same way the scenarios verify `qqx` (`tools/scenarios/i18n-rtl-layout.mjs`, `i18n-language-switch.mjs`) plus by eye: every theme, both directions, Settings and the connect form.

## Deploy rebranding vs translation

A deploy (an IRC network shipping its own client) overrides strings through `config.json`'s `strings` object; users' translations live in `.po` files. Resolution at runtime, first match wins:

**branding override → active locale catalog → `en` → the key itself**

(`client/js/branding.ts` for non-Vue callers, `useI18n().t` for components — one chain.) The override is the deploy's voice — in the deploy's language — and wins in every locale, translation included: a German user on a deploy that overrode `connect.submit` sees the deploy's wording. Any key in the English catalog may be named in `config.json` (see `docs/resources/branding.md` § `config.json` schema); `.po` files carry translations, `config.json` carries the deploy's own copy. The two mechanisms do not overlap.

The chain is uniform where the reader reads in-page copy: `useI18n().t`, `useI18n().tCount` and the splash loop in `activate()` all resolve through one override-aware helper (`brandingT()` in `client/js/branding.ts`), and the override interpolates its `{var}`s exactly as a catalog entry would — a plural key's override is the flat template, with `{count}`/`{n}` filled in. (`brandingString()` — the pre-i18n non-Vue entry point — resolves its own equivalent chain: string override → core resolver; same result, separate path.) Some bypasses are known and deliberate (the Task 4 ruling, documented):

- **The IRC layer resolves through core `t`** (`client/js/irc/**` imports from `i18n/core.ts`, not the Vue binding), so its status strings bypass overrides by ruling: they are catalog copy, not the deploy's voice.
- **The same is true of the Vue-free modules that import core `t` directly**: `client/js/helpers/contextMenu.ts`, `client/js/helpers/mediaTrustMenu.ts`, `client/js/socket-events/connection.ts`, `client/js/socket-events/msg.ts` and `client/js/upload.ts` (its thrown `UploadError` messages). A deploy overriding `menu.*`, `link.*`, `connection.*` or `upload.*` keys reaches only the pages' chain — these surfaces keep catalog copy. New Vue-free modules should make the same choice deliberately and note it here.

## For developers: adding or changing a string

- New UI strings go through `t()`/`tCount()` (`useI18n()` in components; core `t` for Vue-free modules; the worker's own resolver for `client/service-worker.js`) — never raw literals in templates, never string concatenation across keys (§ Placeholders).
- Register the key in the pot with `tools/i18n/add.ts`:

  ```sh
  npx tsx tools/i18n/add.ts <key> "<msgid>" [--plural "<msgid_plural>"] \
    --context "<what the label is and does>" --loc <file:line>
  ```

  The context lines are translator- and MT-facing documentation: say what the label is, where it appears, and what each `{var}` carries — including _verbatim_ markers for user content (`{message} is the verbatim technical message — never translate its content`). `add.ts` upserts idempotently, keeps the pot sorted, and never invents translations.

- Run `yarn i18n:compile` after pot changes (the compiled `en.json`/`qqx.json` and `available.ts` are committed, so a stale pot is a visible diff), and `npx tsx tools/i18n/check.ts` — or just let `yarn test`'s live-tree assertion catch the drift.
- `check.ts` reads call sites with a deliberately simple regex, so call sites are written `t("key")` — double quotes, no concatenation, no computed keys.

## Fragments around interactive elements

A few keys keep an element inside the sentence, so the translation covers the text on one side of the element only — the frame key is a fragment by design: a system message's interactive `<Username>` (context menu, colour, mode prefix; `msg.invited`, …), or the Aliases intro's literal `<code>` tokens (`$1`, `$*` — syntax, not prose). Word order _inside_ each fragment is free; the fragments cannot cross the element. The `#.` context of such keys says so. This is the one deliberate exception to the whole-phrase rule, and it exists because the element is functionality or literal markup, not text.
